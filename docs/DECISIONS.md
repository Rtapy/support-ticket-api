# Decisions

1. **Stack:** Django + Django REST Framework + **PostgreSQL** for development and tests; no SQLite fallback. Database credentials come from environment variables.
2. **Architecture:** One Django backend with a `tickets` app; business mutations live in a small service layer. No extra infrastructure or frontend.
3. **Identity and roles:** Built-in Django User/Groups and Admin. `is_superuser` = Admin in the ticket API; `Support` group = Support; other active users = Employee. `is_staff` is not an API support role. User/group management follows Django Admin's built-in permissions, without an additional custom Admin role or superuser-only restriction. Use DRF TokenAuthentication; no custom auth/user-management API.
4. **Models:** `Ticket`, `TicketMessage`, `TicketStatusHistory`; use Django's User model. Ticket/message references and audit records are protected against cascading hard deletion.
5. **Defaults:** New ticket = `OPEN`, unassigned; priority = `LOW | MEDIUM | HIGH` (default `MEDIUM`).
6. **Normal status transitions:** `OPEN → IN_PROGRESS | RESOLVED`, `IN_PROGRESS → RESOLVED`, `RESOLVED → CLOSED`. No direct `CLOSED → IN_PROGRESS` or no-op transitions.
7. **Reopen:** Dedicated action only for Support/Admin; `RESOLVED | CLOSED → OPEN`. Employees may close only their own `RESOLVED` tickets; closed tickets cannot receive messages until reopened.
8. **Assignment:** Support/Admin may assign to an active Support member (including self) or unassign. Support/Admin can access every ticket; employees only their own.
9. **Messages and history:** Authorized ticket readers can see its messages; no private notes. Record an initial `NULL → OPEN` event and exactly one append-only history event per effective status change.
10. **API surface:** Explicit ticket, message, assignment, status, close, reopen and history endpoints; status filtering on ticket list. Support/Admin may submit a reply with an optional status change in one request. No generic edit, delete or user-management endpoints.
11. **Consistency and race conditions:** For *every mutation of an existing ticket*, enter `transaction.atomic()`, acquire the ticket row using PostgreSQL `select_for_update()`, then recheck permissions, current state and transition rules **after locking**. Commit message/status/history/timestamps together; avoid reading a stale status before the lock. Verify concurrent transitions against PostgreSQL.
12. **Deletion:** Ticket and message use logical-delete fields; no public DELETE endpoint. Block physical deletion through supported admin/application paths and preserve history. Logically deleted tickets remain visible to their owner and to Support/Admin in list, detail and history endpoints. Ticket responses include `is_deleted` and `deleted_at` so clients can control presentation; logical deletion does not expand ownership access.
13. **Scope:** Cursor pagination and Swagger/OpenAPI documentation are approved. Advanced search, notifications, attachments, frontend and deployment remain outside scope unless explicitly requested.
14. **Enforcement boundary and limitations:** Supported ticket mutations go through transactional services; ticket/message/history Admin screens are read-only. Server-controlled creation fields are ignored if submitted. ORM deletion/history guards are not database triggers or direct-SQL restrictions; direct ticket creation outside the service does not automatically record initial history. There is no public logical-delete/restore action or token-login endpoint; use Django Admin for users/groups and DRF's `drf_create_token` command for tokens.
15. **Pagination:** Use DRF's built-in CursorPagination with a fixed page size of 20 for `GET tickets/`, `GET tickets/{id}/messages/` and `GET tickets/{id}/history/`. Responses use `next`, `previous` and `results`, without a total count or client page-size control. Ticket ordering remains `-created_at, -id`; messages use `created_at, id`; history uses `changed_at, id`. Ownership/status filtering precedes pagination. Clients follow opaque links without modifying their cursor. Detail and mutation response shapes are unchanged.
16. **API documentation:** Public Swagger UI at `/api/docs/` and OpenAPI schema at `/api/schema/`, generated by drf-spectacular with local sidecar UI assets. Documentation access does not authorize ticket requests: all ticket API operations still require `Authorization: Token <key>`. No token-login endpoint or additional user/role system is introduced. The schema documents all ten operations, cursor envelopes, server-controlled fields, role/workflow rules, examples and error responses.
